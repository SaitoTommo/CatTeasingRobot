# ESP32 Web 掉线排查与修复（2026-10-05）

## 实施计划

1. 检查 HTTP 服务、网页并行轮询和 Wi-Fi 连接管理，区分代码风险与实际掉线证据。
2. 修复连接回收与冗余取图，补充网络诊断；运行网页回归测试及 ESP32 离线编译。
3. 将事情经过、验证数据和待测项发给“整理项目日志与问题数据”对话，更新项目日志。

## 现象与证据边界

用户反馈 Web 经常掉线，并确认是整个网页显示“连接中断”。该提示来自 /api/state 请求或后续解析、界面更新失败；不是 Wi-Fi 已断开的直接证明。

本次只读请求历史地址 192.168.137.188 和最近上传记录中的 192.168.137.130，分别在 5 秒、6 秒超时。没有取得当前设备快照，也没有确认当前 IP、热点状态和供电。不能据此认定 HTTP 阻塞、Wi-Fi 断连、设备复位或内存不足中的哪一种是实际根因。

随后用户确认当前地址为 192.168.137.130，再次读取成功，固件仍为 0.29；ms=11637579、UART/IDLE、heap=13904。进一步完成以下只读采样（在主机离线编译同时进行，不是隔离的网络性能基准）：

- 连续 5 次 PowerShell 状态读取均成功，客户端调用到 JSON 解析完成的耗时为 8237、6389、6504、5414、9607 ms；配置的 TimeoutSec=6 没有形成严格的总时限。这些值不能视为 ESP32 单独处理耗时。
- 五次快照 ms 从 11670924 增到 11698931，frameSeq 从 57759 增到 57899；heap 为 13656、13904、13908、13640、12192 B。该窗口未看到 uptime 回退或摄像头停止，少量快照不能证明内存泄漏。
- curl 禁用代理、连接超时 2 秒、总超时 6 秒，3 次请求的 TCP 建连为 15.397/26.928/3.896 ms；首字节为 5891.852/1182.486/80.069 ms；总耗时 6010.429/1903.665/4374.202 ms。第 1 次虽收到 HTTP 200，只收到 4249/22122 字节，curlExit=28，不能算成功；第 2、3 次完整收到 22135/22128 字节，curlExit=0。
- 结果支持状态请求有明显延迟/不完整传输，能触发网页 4 秒超时；建连快而首字节或正文慢，尚不能单凭这 3 次样本区分服务排队、Wi-Fi 传输和客户端因素。不能声称已找到唯一根因。

证据在 `evidence/web-recovery-20261005/`：http-before-samples.json、curl-before-samples.json、before-state.json 和 curl-state-*.json。curl 第 1 份文件是截断正文，不应当作有效 JSON 快照使用。

## 源码确认的问题

- Arduino ESP32 核心 3.3.12 的 HTTP 默认值：max_open_sockets=7、lru_purge_enable=false、recv/send 等待 5 秒。现有 80 端口沿用默认值，承载状态、配置输入和多种 JPEG 接口，缺少旧连接回收。慢客户端会占用串行 HTTP 服务处理时间；连接用尽时存在新请求被拒绝的风险。这是代码风险，尚无实际连接耗尽记录。
- 前端 /api/state 每轮完成后等 600 ms；猫原图每轮等 200 ms；测试状态闲置时也每轮等 1000 ms。帧率测试开启时，状态间隔 250 ms，原图间隔 100 ms。未变化的猫帧虽可返回 204，仍持续发起请求。
- 网页对状态请求设 4 秒超时，短于服务单次发送可能等待的 5 秒；图片发送若先占住服务，状态请求可能排队超过网页超时。实际是否发生仍需测量。
- Wi-Fi 核心默认 _autoReconnect=true，且重连依赖断开原因；不能说“原来完全没有自动重连”。应用缺少断开原因、重连记录和持续失败后的补充重试。

以上轮询间隔是配置，不是实测请求频率。

## 本次处理

固件版本：ESP32_CAT_HOST_0.30_WEB_RECOVERY。

1. 两个 HTTP 服务启用 LRU 连接回收；收发等待由 5 秒改为 2 秒，降低慢客户端占用时间。保留现有连接数，不盲目增加 socket。
2. /api/state 获取控制器锁最多等待 250 ms，忙时返回 503，供前端重试；这不保证其他接口或内层帧锁没有等待。
3. 猫预览仅在状态快照表示有新结果时取图；无图、同一结果和设备断线时跳过。检测框仍使用与 JPEG 配对的元数据，复位或断线后迟到的图像丢弃。
4. 猫原图检查间隔 350 ms；帧率测试状态为开启 600 ms、闲置 3000 ms，测试图像间隔 350 ms。只调整 Web 展示请求，不调整模型推理和行为控制节奏。
5. 状态请求失败立即将读数标为不可用、禁用相关控制、释放实时视频连接并暂停辅助轮询；重试等待 1200/2400/3000 ms，成功后恢复 600 ms。恢复只读数据，不重发操作命令。
6. 显式启用核心自动重连；持续未连接时每 30 秒尝试 reconnect。保留软 AP。关闭 Wi-Fi modem sleep 以减少网络延迟，代价是可能增加功耗；改善幅度待真机验证。
7. 新增 network 快照：连接状态、RSSI、断开次数/原因/时间、补充重连次数、省电状态、resetReason、最小空闲 heap、最大连续内部空闲块。Wi-Fi 回调仅入队，loop 负责记录日志，避免回调直接操作控制器状态。
8. 根据实际约 22 KB 状态响应，网页新增 afterLog 游标增量读取，每次最多取最近 40 条新增日志，在浏览器保留最多 160 条、去重并在设备复位时清空。启动前历史及两次读取之间超过 40 条的日志可能不进入网页历史；完整无参数 /api/state 和 USB state 仍保留最近 160 条，诊断导出应使用完整接口。新增 logSeq/logsFromSeq 说明日志范围。

同一旧版快照的离线序列化估算为：完整 160 条日志 22132 B、只留最近 40 条 11752 B、无新日志 8293 B。新版增加 network 和游标字段，不能将这些估算写成新版实测传输尺寸或速度提升。对应 payload-estimate.json。

没有改变 Uno 固件、巡游路线、运动参数或猫互动状态机；没有打开串口、复位、刷板或运行机器人。

## 验证

- 网页回归测试：45/45 通过。包含新结果取图、同帧跳过、断线暂停/恢复、迟到图丢弃、状态断线禁用控制和退避恢复，以及增量日志去重、历史保留、容量限制和复位清空。
- 内嵌网页 gzip 无损校验通过：78,949 字节压缩至 27,818 字节。
- 最终 ESP32 离线编译通过（包括增量日志和最终网页）：Flash 3772038/8257536 B、静态 RAM 85296/327680 B。静态 RAM 数值不是运行时堆余量。首次编译受 sandbox 对 Arduino15 符号链接的访问限制，获得离线编译权限后成功；没有安装新核心或刷板。
- 真机 Web 稳定性、实际 RTT/P95、断线原因、热点关闭后的恢复、IP 改变和功耗：待测；源码修复尚未刷入设备。

## 建议的人工验收

在确认停车后刷入 ESP32，刷新页面并核对版本，再分别运行状态页面、识别预览、帧率测试各 10 分钟；记录 HTTP 成功率、连续失败长度和 network 信息。开关热点检查重连，并核对重新取得的 IP。对照设备 ms 是否回退及 resetReason、断开计数和最大连续空闲块，区分复位、Wi-Fi 和 HTTP 故障。真实 motion/Uno 行为仍需单独验收。

## 用户授权上传后的结果（2026-10-05）

用户随后明确要求“上传吧”，上述尚未上传是上传前状态。

- 上传前读取 COM11：0.29、IDLE/SIM_UNO、motorId=0、motorRunning=false、stopPendingId=0、stopUnconfirmed=false、debugBusy=false。该读取为 ms 约 588 的启动快照；不能把此前运行模式 UART 写成整个过程中始终保留。
