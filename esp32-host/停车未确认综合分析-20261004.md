# STOP_UNCONFIRMED 综合分析

范围：离线核对下载目录日志1–38（不同固件、不同运行，仅保留各自末尾160条），重点26/27/32–35/37/38；对照当前ESP与Uno源码及已保存的双USB串口采集。未改代码，未操作设备、浏览器或Computer Use。分析证据保存在`evidence/stop-unconfirmed-analysis-20261004`。

## 结论及证据边界

STOP_UNCONFIRMED是“没有收到与当前STOP编号匹配、格式正确、CRC通过的DONE ... MOTOR_STOPPED”，并非直接测得电机没有停。它是多个故障最后汇聚的保护状态。综合证据最集中指向命令通信链路间歇失效；早期还有独立的Uno自行重启，以及已经定位并修复的停车输出和恢复解析缺口。不能将所有事件归因于猫状态重叠、PWM下限、摄像头算力或某一种电气故障。

最新日志38中，Uno→ESP的诊断回传仍持续，ESP→Uno命令及其事务回复没有闭环。问题定位在命令从ESP发送、经线路/电平转换、到Uno D12软件串口接收、组帧、执行及回复这一段；仅凭ESP发送日志无法确定字节实际到达哪个引脚、在哪层丢失。还不能确定是线路/转换器、软串口接收状态/时序、发送端故障，还是其他干扰。不把候选当作确认根因。

## 当前信息流

1. 策略要停车，清理旧运动请求并生成`C <id> STOP*<CRC>`。
2. ESP UART发出，Uno D12 SoftwareSerial以57600接收并组帧；命令经CRC、编号和字段校验后执行。
3. 当前Uno STOP路径调用abortMotion，6.10先执行stopOutputs，再取消动作；回传带CRC的`AK <id>`和`DONE <id> MOTOR_STOPPED`。
4. ESP只有匹配当前stopPendingId的有效DONE才解除停车门禁。心跳、PWM0遥测、别的编号DONE、自己的命令回显都不能替代它。
5. 初发后约每300ms重发同编号，最多3次；约1.2秒仍无确认则报STOP_UNCONFIRMED，阻止后续运动。
6. 适用时进入最多4轮自动恢复：清ESP应用层解析/遥测/策略状态→新STOP→确认后结束旧会话→读正确几何配置→恢复会话。STOP无法确认，后续同步步骤就不会执行。

`resetLinkState()`当前清应用层缓存和事务标志，不重启Uno，也没有对ESP硬件UART执行end/begin，不能把它称为物理串口重建。手动SIM↔UART也会重发停车/会话/配置并清状态；某次切换成功只能证明该时间附近恢复，不能证明线路根因或切换本身必定有效。

## 历次证据的分类

| 日志/证据 | 已确认的现象 | 不能混同的解释 |
| --- | --- | --- |
| 26、27 | 扫描交接失败前后，ESP收到自己完整带CRC的SR/VR/STOP；停车首发与重发不能闭环 | UART_LOOPBACK不是Uno执行确认，不是猫一直被检测为true导致STOP失败 |
| 32、33 | STOP同编号连续回显，恢复失败；手动切换附近后来收到真正停车DONE | 有命令回显的链路异常；一次切换恢复不是可靠性修复证明 |
| 34 | 前两轮STOP回显；第三轮真正STOP268、SESSION_STOP270、正确CONFIG271已收到，恢复却失败 | 底层异常之外，旧恢复状态没有消费正确配置，是已复现的软件缺口 |
| 35 | 684遥测DONE收到但缺片；旧ESP挂起查询约5251ms；后续回显和第三轮配置误判再次出现 | 部分快照必须拒绝，但事务不释放是独立软件问题；不能把缺RPM证据等同轮子正在转 |
| 37 | 前面GET_TELEMETRY连续超时，并出现ERROR0 BAD_ENVELOPE；29460ms起恢复完整遥测 | 命令字节/组帧异常可间歇恢复；最终STOP_UNCONFIRMED标志与查询恢复可以同时存在 |
| 38 | 四轮STOP完全无回复，只有Uno诊断在继续，手动切换两次也没恢复 | 与34/35“回复到了但恢复没消费”不同，这次未取得恢复所需的停车回复 |
| post-v025/COM10与log34采集 | 非人工操作期间捕到READY/启动残留，用户确认未复位 | 存在真正自行重启；启动残留步骤/命令不是复位原因，不能直接断言欠压 |

所选窗口UART_LOOPBACK条数：26为7，27为10，32为12，33为10，34为12，35为10；38为0。它们是日志记录数，不是全程丢包率。当前Uno源码不主动回显完整`C ...`命令，所以这些回显不是正常ACK。究竟在哪个线路/转发环节形成回显，日志尚不能定点。

## 已修复与仍未解决

- Uno6.10已修复abortMotion在MOTION_NONE时提前返回、跳过stopOutputs的缺口：此前可能“回了停车DONE，但输出未清零”。这是另一个方向的问题，不能解释所有无DONE故障。
- ESP0.29已将严格CONFIG解析用于正常启动与恢复，也在可信匹配遥测DONE但缺片时释放pending并重试；恢复增加到4轮。日志38确实执行了4轮，仍无STOP回复，不是旧三轮配置误判重现。
- 真正的底层命令链路间歇异常、自行重启的物理/软件根因仍未闭环。更多重试只对短暂损坏有帮助；通道持续不收命令时重复同类请求无法自行修好。
- 故障恢复清空遥测，因此网页显示“没有读数”；诊断心跳仍更新lastUnoAgeMs，容易让用户误认为所有功能在线。故障文案应区分“收到心跳”“命令有响应”“停车已确认”，不要只用“Uno已连接”概括。

## 下一步定位建议（本轮未执行）

在故障发生前后保存连续双USB原始数据和ESP日志，避免160条窗口覆盖起因；不先用切换模式抹掉故障现场。增加只读诊断计数：Uno D12实际收到字节数/完整行数/CRC拒绝数/最后合法命令编号，以及ESP发送计数、停车编号和CRC拒收理由。仅rxOverflow计数不能区分“没字节到达”和“字节到了但无完整行”。

关键分叉：ESP记录STOP发送后，D12是否实际出现该帧；若没有，看ESP TX、转换器及接线；若有但无完整解析，看软件串口和组帧；若Uno已执行并在D1发出有效DONE、ESP未确认，看回传线路和ESP接收解析。用同编号对照而不是心跳在线。需要引脚波形或更细的接收计数才能最终定点；本轮不擅自改程序或进行电机/烧录测试。
